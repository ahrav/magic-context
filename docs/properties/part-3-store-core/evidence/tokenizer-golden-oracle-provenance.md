# tokenizer-golden-oracle-provenance

## Discovery trigger

`crates/mc-tokenizer/tests/token_golden.rs:1-4` describes the test's purpose:
"Differential golden: assert the Rust port's ordinary byte-BPE encoding is
bit-identical to `ai-tokenizer`'s `claude` encoding across an adversarial corpus.
The fixture (`testdata/token-golden.json`) is generated by
`gen/gen-token-golden.ts` from the exact TS tokenizer the plugin uses."

The phrase "the exact TS tokenizer the plugin uses" is a claim about a specific
version of an external package. A differential test whose expected values are
generated from the thing under comparison can only pin the comparison at the
moment of generation, and only if the moment is recorded. So the question is
whether the fixture records which oracle produced it.

## Evidence trail

The fixture's schema, enumerated rather than sampled. I read
`crates/mc-tokenizer/testdata/token-golden.json` and computed the union of keys
across all entries:

- The document is a flat JSON array with **36 entries**.
- The key union across all 36 entries is exactly `{label, text, ids}`.
- There is no `version` field, no `aiTokenizerVersion`, no `generatedAt`, no
  vocab digest, no encoding name, and no generator revision.

The consumer side confirms nothing more could be checked even if present:

- `crates/mc-tokenizer/tests/token_golden.rs:14-19` defines
  `struct GoldenCase { label: String, text: String, ids: Vec<u32> }`. Serde
  ignores unknown fields by default and the struct has no `deny_unknown_fields`,
  so a provenance field added to the fixture would be silently dropped.
- `crates/mc-tokenizer/tests/token_golden.rs:21-24` loads the fixture with
  `include_str!` and deserialises to `Vec<GoldenCase>`.
- The four tests are `encode_ordinary_matches_ai_tokenizer_ids` (`:26-45`),
  `estimate_tokens_matches_golden_counts` (`:47-57`), `empty_text_is_zero`
  (`:59-62`), and `deterministic_across_calls` (`:64-73`). None reads or
  validates a provenance field, and none computes a digest of
  `assets/claude.tiktoken` to compare against a recorded value.

Corpus breadth, measured:

- The 36 labels cover empty, single space, ASCII, a punctuated sentence,
  contractions, a leading-space word, multi-space and tab and newline runs,
  trailing whitespace, digit forms, alphanumeric identifiers, punctuation runs,
  symbol soup, JavaScript source, JSON, a filesystem path, special-token
  substrings as literals (twice), Latin accents, CJK, emoji with ZWJ sequences,
  Cyrillic and Greek, mixed script, line-ending variants including CRLF, a
  repeated word, a long word, a URL with a query string, a prose paragraph, RTL
  scripts, combining marks, zero-width and format characters, control characters,
  astral-plane text, a long single-character repetition, a transcript, a stack
  trace, and a large mixed blob.
- Across all 36 cases the corpus uses **564 distinct token IDs**. The vendored
  vocab has **64,995 entries**. That is **about 0.87% of the vocab exercised**.

The strength being recorded: `token_golden.rs:6-9` explains that asserting the
full ID sequence rather than the count "proves the merges are identical — a
count-only check could pass on a wrong-but-same-length encoding", and
`:31-39` implements exactly that, accumulating every mismatch before asserting so
a single run reports all failures. That is a well-built differential test. The
problem is not its assertion strength; it is what the expected values are
anchored to.

One nuance about normalisation, checked because the corpus looked like it might
pin it. Running Unicode normalisation over each case's text: `combining-marks`
(`"é à ñ ö café Ǻ"`) is NFD and not NFC, while `unicode-accents`, `cjk`,
`cyrillic-greek`, `mixed-script`, and `large-mixed-blob` are NFC and not NFD. So
the corpus does contain one decomposed sample, which means it exercises the fact
that the tokenizer does not normalise its input. But it never contains the *same*
text in both forms, so it does not pin "NFC and NFD of the same string encode
differently" as a relation; it happens to include one decomposed string among
several composed ones.

## Failure scenario

Upstream `ai-tokenizer` ships a change to its `claude` encoding: a vocab
addition, a `pat_str` adjustment, or a merge-table correction. The plugin picks
it up on its next dependency update, so the TypeScript side of the system now
tokenizes differently. The Rust port is unchanged and is now unfaithful.

Someone notices a mismatch, or routinely regenerates fixtures as part of the
update, and runs `bun crates/mc-tokenizer/gen/gen-token-golden.ts`. The fixture
is rewritten with the *new* TypeScript output. If the Rust port happens to still
agree on all 36 strings, the suite is green and nobody learns anything. If it
disagrees, the failure appears as a Rust-side bug rather than as an upstream
change, because nothing in the diff says which oracle moved.

The worse variant needs no regeneration at all. Because only 0.87% of the vocab
is exercised, an upstream change confined to token sequences absent from the 36
strings leaves the suite green with no regeneration, and the divergence sits
undetected until it affects a real session's m0 rendering. At that point the
symptom is a busted cache prefix on resume, which is
`crates/mc-tokenizer/src/lib.rs:13-19`'s stated failure mode, several layers away
from its cause.

A second, cheaper accident: someone edits `assets/claude.tiktoken` (to add a
token, to fix a line, to normalise whitespace). Since no test digests the asset,
the only signal is whether one of the 36 cases changes. A vocab edit touching an
unexercised rank changes every future count silently.

## Timing windows and dependencies

No runtime window. The window is developmental and is precisely the regeneration
step: the moment a human runs the generator, the expected values are re-anchored
to whatever the oracle is at that instant, and the test's meaning changes without
its code changing.

Dependency: this record is the faithfulness counterpart to
`tokenizer-cross-process-determinism`. The crate doc separates the two
explicitly at `crates/mc-tokenizer/src/lib.rs:16-19`: determinism is the runtime
invariant, faithfulness to the TypeScript is "a FAITHFULNESS goal (validated by
the differential golden in `tests/`), not a runtime invariant". Both matter, and
neither substitutes for the other.

Note also that the same provenance gap exists for the decay golden:
`crates/mc-core/src/decay.rs:252` loads `../testdata/decay-golden.json`, generated
by `crates/mc-core/testdata/gen-golden.ts` per the comment at `:248-251`, and the
`Golden` struct at `:240-244` deserialises only `tier_cases` and
`pressure_cases`. Whether that fixture carries provenance is a question for
whoever owns the decay-golden fixture; the pattern is the same and worth noting
once here.

## What a test must construct

1. Provenance fields in the fixture, written by the generator: the resolved
   `ai-tokenizer` version, the encoding name, and a digest of the vocab source the
   generator read.
2. A digest of `assets/claude.tiktoken` recorded in the fixture, plus a test that
   computes the digest of the embedded asset at runtime and compares. That closes
   the vocab-edit hole for the cost of one hash. `mc-core` already depends on
   `sha2` (`crates/mc-core/Cargo.toml`), so the primitive is available in the
   workspace.
3. A test that asserts the provenance fields are present and non-empty, which
   requires adding them to `GoldenCase` or to a wrapper struct, since the current
   flat-array shape has nowhere to put document-level metadata. Changing the
   fixture from a bare array to `{provenance: {...}, cases: [...]}` is the
   structural prerequisite.
4. Corpus expansion driven by vocab coverage rather than by intuition: sample
   texts that exercise a stated fraction of the 64,995 ranks, and record the
   achieved coverage in the fixture so a regression in breadth is visible.

Semantics: `reachable`. This is location coverage, not situation coverage: a
specific verification step (the provenance and digest comparison) must execute.
It is not `sometimes`, because there is no operational state to reach; the step
either exists and runs or does not exist. It is not `always`, because the claim
is about a check being present rather than about a condition holding at every
evaluation. Recording it as a `reachability` type is deliberate and gives the
part at least one non-safety record.

## Investigation log

### Q: Does `ai-tokenizer` expose a version the generator can stamp?

- Sources examined: `crates/mc-tokenizer/gen/gen-token-golden.ts` and
  `crates/mc-tokenizer/gen/gen-claude-vocab.ts` exist in the tree;
  `crates/mc-tokenizer/src/lib.rs:5-11` names the TypeScript call shape
  (`Tokenizer(claudeEncoding).encode(text, "all").length`) and the vocab source
  (`ai-tokenizer/encoding/claude`).
- Findings: the crate documents which upstream module it ports and which call it
  matches, so the generator clearly imports from the package and could read its
  version from `package.json` or from an exported constant. Whether the package
  exports a version constant I did not establish, but the packaged
  `package.json` version is always available to a Bun script at generation time,
  so a stamp is achievable regardless.
- Missing evidence: the `ai-tokenizer` package's export surface, and whether it
  is a direct dependency with a resolvable version or vendored.
- Conclusion: unresolved, needs the `ai-tokenizer` package surface. The weaker
  form (stamping the resolved `package.json` version and a vocab digest) is
  achievable without any upstream cooperation, so the question does not block the
  fix.

### Q: Should the vocab asset carry a checked-in digest?

- Sources examined: `crates/mc-tokenizer/src/lib.rs:33-37` (the asset's doc,
  which explains it is "unified from `ai-tokenizer/encoding/claude`'s string +
  binary encoders. Embedded at build time so there is no runtime file read or
  network fetch"), the asset's measured shape (64,995 lines, two fields each, no
  duplicate keys, no duplicate ranks), and the absence of any digest check in
  `token_golden.rs`.
- Findings: the asset is generated by `gen/gen-claude-vocab.ts` and is the single
  source of every token count the system produces. An accidental edit is
  low-probability but total in effect: every count changes for any text touching
  the edited rank. A digest check is a few lines and turns a silent change into a
  build failure. The cost is that a deliberate regeneration requires updating the
  digest, which is the intended friction.
- Missing evidence: none.
- Conclusion: needs human input on whether to add it, since this catalog records
  properties and does not make fixes. Recording the reasoning so the decision can
  be made on the evidence rather than re-derived.

### Q: Does CI run the tokenizer tests on more than one platform?

- Sources examined: `.github/workflows/ci.yml`. I enumerated the `runs-on` and
  `matrix` lines: the file contains many `runs-on: ubuntu-latest` jobs and one
  matrixed job, "Shared memory source build (${{ matrix.os }})", whose
  `runs-on: ${{ matrix.os }}` and `matrix` block are the only multi-OS
  configuration present.
- Findings: the tokenizer tests run under the ubuntu-only Rust jobs. There is no
  macOS, Windows, musl, big-endian, or aarch64 job that would execute
  `token_golden.rs`. So the golden validates one target.
- Missing evidence: whether any other workflow file
  (`shm-hardening-optin.yml`, `retrieval-benchmark.yml`,
  `historian-eval.yml`, `claude-code-review.yml`) runs the Rust test suite on a
  different target. I checked the `runs-on`/`matrix` lines of `ci.yml` only.
- Conclusion: unresolved, needs a full workflow survey. The finding for this
  record stands regardless: the golden cannot detect a platform-specific
  divergence on a platform CI does not run, and the primary CI file runs one.
